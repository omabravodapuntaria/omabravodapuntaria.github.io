WOW64CPU.DLL

the binary translator DLL for running x86 programs under WOW64 on AMD64 Windows
last revised for this build · undocumented by Microsoft · derived from live observation, not from any Microsoft source

the module

x64 %SystemRoot%\System32\wow64cpu.dll ~40 KB image

WOW64CPU.DLL is one of the small set of 64-bit binaries that Windows allows to be mapped into an otherwise 32-bit process. Together with WOW64.DLL and WOW64WIN.DLL it forms the WOW64 subsystem on x86-on-AMD64 Windows: WOW64.DLL drives process and thread setup, WOW64WIN.DLL thunks the Win32 USER/GDI system calls, and WOW64CPU.DLL supplies the actual mode switch — flipping the processor between 32-bit compatibility mode and 64-bit long mode around every system call the 32-bit program makes.

It is not loaded through an ordinary LoadLibrary call. It is mapped by NTDLL's own WOW64 initialisation code, inside Wow64LdrpInitialize, before any user-mode code in the new process has had a chance to run. A 32-bit process trying to LoadLibraryW(L"wow64cpu.dll") for itself gets ERROR_BAD_EXE_FORMAT — the ordinary loader path correctly refuses to map a 64-bit image into a 32-bit address space. The module is only reachable, as far as anyone outside Microsoft can tell, by attaching a debugger to a process that already has it loaded and switching the debugger's effective machine to amd64.

The role WOW64CPU.DLL plays is defined entirely by its caller. Two mechanisms exist for pointing a WOW64 process at a binary translator DLL other than the built-in one: a per-image registry override under HKLM\SOFTWARE\Microsoft\Wow64\x86\<image name>, used by the ARM64 builds to substitute XTAJIT.DLL or WOWARMHW.DLL, and it is this substitutability that defines the exported contract documented below — every export here exists because WOW64.DLL's loader, CpuLoadBinaryTranslator, resolves it by name and expects it to behave identically regardless of which translator supplies it.

why so little of this is documented anywhere
A binary translator DLL is an internal implementation detail of the loader, not a public Win32 surface — nothing in the Windows SDK ever calls these functions directly, so there was never a reason for Microsoft to write a page about them. The only pre-existing public information is the bare list of resolved export names, visible on the Wine reimplementation's own (also largely undocumented) WOW64CPU.DLL, and scattered call-stack fragments in unrelated crash reports and security write-ups. Nothing describing calling convention, argument meaning, or behaviour appears to exist in public form prior to this page.

wow64cpu!BTCpuGetContext

exportedx64 fastcall

Retrieves the 32-bit register context of a thread running under WOW64, into a caller-supplied WOW64_CONTEXT-shaped buffer. It is the function standing behind Wow64GetThreadContext and, less obviously, is also invoked internally by WOW64WIN.DLL around callback dispatch, to snapshot the guest register state before delivering a callback into 32-bit code. 

// derived; no header declares this
NTSTATUS BTCpuGetContext(
    HANDLE  ThreadHandle,
    PVOID   Reserved,        // unused; value discarded on entry
    PVOID   Reserved2,       // unused by any observed call site
    PWOW64_CONTEXT Context  // in/out — caller pre-sets ContextFlags
);

parameters

registerrole
rcxThread handle. Observed as the current-thread pseudo-handle (-2) in every trace taken, but the function explicitly compares against -2 and falls back to a general path otherwise, so real thread handles are accepted.
rdxNot used. Zeroed immediately on entry regardless of what the caller passes.
r8Not used by the caller in any observed call; the function reserves its own local scratch for this slot.
r9Output buffer. The context is written here. The caller is expected to have set the flags field (offset 0) before the call, in the usual CONTEXT.ContextFlags convention.

behaviour

  1. Calls RtlWow64GetCpuAreaInfo for the current thread. A negative status here is treated as unrecoverable: the function fast-fails via int 29h rather than returning an error, meaning callers can assume this step always succeeds in a correctly functioning process.
  2. If the target is the current thread and a flag returned by that call is set, a fast path is taken: the context is copied straight out of the thread's cached CPU area via RtlCopyContext, using the flags the caller already placed in the output buffer.
  3. Otherwise — a different thread, or the cached-context flag not set — it falls back to NtQueryInformationThread with information class 0x1D (ThreadWow64Context), the ordinary kernel-mediated path.
  4. On the fast path only, if bit 30 of the returned flags is set, the function additionally ORs 0x88000000 into the output context's flags before returning — consistent with signalling that extended (XSTATE) data is present.
observed in the wild
Every live hit captured for this page arrived not from an application calling Wow64GetThreadContext directly, but from wow64!CpuGetContext → Wow64KiUserCallbackDispatcher, triggered by a 32-bit program's GetMessage call. WOW64WIN uses this function internally to snapshot guest state before dispatching a window-message callback, not only in response to an explicit debugger-style context request.

wow64cpu!BTCpuSetContext

exportedx64 fastcall

The write counterpart to BTCpuGetContext: applies a caller-supplied 32-bit context to a thread running under WOW64. Its structure mirrors BTCpuGetContext closely, with one deliberate asymmetry around segment selectors. 

// derived; no header declares this
NTSTATUS BTCpuSetContext(
    HANDLE  ThreadHandle,
    PVOID   Reserved,
    PVOID   Reserved2,
    PWOW64_CONTEXT Context   // in — context to apply
);

parameters

registerrole
rcxThread handle, same convention as BTCpuGetContext (-2 = current thread).
rdxNot used; zeroed on entry.
r8Not used by the caller; local scratch.
r9Input buffer — the context to apply.

behaviour

  1. Same opening as BTCpuGetContext: RtlWow64GetCpuAreaInfo, same int 29h fast-fail on failure.
  2. Same current-thread-and-cache-valid check to choose between the fast and slow path.
  3. Slow path: NtSetInformationThread, information class 0x1D — the direct mirror of the get-context slow path.
  4. Fast path is not a plain mirror of get. The incoming context's flags are masked against 0x10010 and compared for an exact match; if that fails, the function additionally compares three specific fields (offsets +4, +0xC, +0x14) of the incoming context against the cached CPU area at the same offsets. Note this is a different, smaller structure than the full guest CONTEXT documented under Structures — these three offsets land early enough in a compact record to plausibly be selector-related fields, but that identification is a hypothesis based on offset position, not a confirmed field name the way the RtlpWow64CtxFromAmd64 fields are. If any of the three differ, the function falls all the way back to the slow, kernel-mediated path instead of writing in place — segment selector changes are not considered safe to apply without going through the kernel. If the selectors are unchanged, the fast path proceeds via RtlCopyContext, with the flags masked by 0x37FFFFFF first.
why the asymmetry
Reading stale segment-selector state back to the caller is harmless, so BTCpuGetContext's fast path has no equivalent check. Writing selectors is a different matter — loading a segment register is a privileged, validated operation, so BTCpuSetContext only takes the fast, in-memory path when the selectors aren't actually changing; any real change is routed through NtSetInformationThread instead.

wow64cpu!BTCpuGetBopCode

exported5 instructions

The smallest export in the module — a two-way selector, not really a "get" in the sense of reading external state. It hands back the address of whichever syscall entry trampoline the process has been configured to use. 

PVOID BTCpuGetBopCode(VOID);

behaviour

Reads the module-global byte CpupSystemCallFast. If it is non-zero, the function returns the address of KiFastSystemCall; otherwise it returns KiFastSystemCall2. No arguments are consulted.

where the flag comes from
CpupSystemCallFast is a one-time decision made during process initialisation: WOW64CPU sets it when the process is not running under the ProcessDynamicCodePolicy mitigation and a call to NtProtectVirtualMemory against KiFastSystemCall succeeds. BTCpuGetBopCode is simply the runtime read side of that earlier decision — every syscall thunk asks this function which entry point to jump to, rather than re-deriving the answer itself.

wow64cpu!BTCpuSimulate

exporteddoes not return

The function that actually runs the 32-bit program. Despite the name suggesting an emulation loop of its own, WOW64CPU's implementation of BTCpuSimulate is a two-instruction trampoline: it calls RunSimulatedCode in a loop that never exits under normal operation. All of the real work — the actual mode switch — lives in RunSimulatedCode, documented separately. 

VOID BTCpuSimulate(VOID);  // noreturn in practice

// the entire body, in full:
BTCpuSimulate:
    sub  rsp, 38h
loop:
    call RunSimulatedCode
    jmp  loop
    ; add rsp,38h / ret below are unreachable in normal operation

observed call sites

Two distinct callers were observed, corresponding to two different purposes:

(1) once, at process start — wow64cpu!BTCpuSimulate wow64!RunCpuSimulation+0xd wow64!Wow64LdrpInitialize+0x122 ntdll!LdrpInitializeProcess ntdll!LdrpInitialize ntdll!LdrpInitializeInternal ntdll!LdrInitializeThunk (2) recursively, from inside the loop itself, after handling one system call — wow64cpu!ServiceNoTurbo+0x9 wow64cpu!BTCpuSimulate+0x9 wow64!RunCpuSimulation+0xd (re-entry, not a fresh call from wow64.dll)

The second trace is a re-entry into the same call, not a second, independent call from WOW64.DLL — it shows that once the 32-bit program makes a system call that can't be handled by the fast "turbo" dispatch path, control comes back up through ServiceNoTurbo and lands back inside the very loop that has been running since process start, rather than BTCpuSimulate being invoked afresh each time.

wow64cpu!BTCpuTurboThunkControl

exported

Installs, or resets, the jump table used for "turbo" system-call dispatch — the fast path that lets common system calls be serviced without a full round trip through Wow64SystemServiceEx. This is the function that populates the table read by TurboDispatchJumpAddressStart. 

NTSTATUS BTCpuTurboThunkControl(
    ULONG Operation   // 0, 1, or anything else
);

parameters

registerrole
ecxOperation selector. 0 installs the turbo dispatch table (the main path); 1 returns immediately with status 0xC000000BB (STATUS_NOT_SUPPORTED); any other value returns 0xC000000D (STATUS_INVALID_PARAMETER).

behaviour of the install path (Operation = 0)

  1. Calls NtProtectVirtualMemory to make the TurboThunkDispatch table region writable.
  2. Fills all 32 entries of the table with the address of a common default thunk handler.
  3. Calls NtProtectVirtualMemory a second time to restore the table's original protection.
  4. Walks the table back, verifying each of the 32 entries is either the default handler or a second recognised handler value; any entry that is neither triggers a fast-fail (int 29h) — a self-consistency check on the table it just wrote, not a check on caller input.
how it's used at runtime
TurboDispatchJumpAddressStart indexes directly into the table this function builds, keyed by the top bits of the system call number (eax >> 0x10). A system call that lands on a populated, non-default entry gets serviced without ever calling ServiceNoTurbo/Wow64SystemServiceEx at all.

wow64cpu!BTCpuProcessInit

exportedcalled once per process

Called once, very early in process startup, from Wow64LdrpInitialize, before BTCpuSimulate's first call. This is where the module's two process-lifetime globals are decided: CpupSystemCallFast, read later by BTCpuGetBopCode, and CpupCpuAreaEnabledFeatures, read later by RunSimulatedCode and by BTCpuThreadInit. 

NTSTATUS BTCpuProcessInit(VOID);  // no arguments consumed

behaviour

  1. Resolves a count from the TEB's WowTebOffset field (offset +0x180C, confirmed via dt ntdll!_TEB); a negative value triggers an extra indirection through another TEB-adjacent field (offset +0x18) before continuing — consistent with the documented meaning of WowTebOffset as the signed offset to the WOW64 TEB, where a negative value is the normal case and other values indicate a different addressing mode.
  2. Sets a flag bit on whatever that resolves to, then checks SharedUserData+0x308 (a KUSER_SHARED_DATA field) against 1. If it matches, the fast-syscall setup below is skipped entirely and the function proceeds straight to the CPU-area-features step.
  3. Otherwise, queries NtQueryInformationProcess (current process, information class 0x2C, i.e. ProcessMitigationPolicy) for the dynamic-code mitigation policy. Failure, or a policy value indicating dynamic code is prohibited, skips the fast-syscall setup and leaves CpupSystemCallFast at its default (off).
  4. If dynamic code is permitted: calls NtProtectVirtualMemory on the page containing KiFastSystemCall. On success, sets CpupSystemCallFast = 1 — this is the flag BTCpuGetBopCode reads on every subsequent syscall dispatch.
  5. Unconditionally, regardless of which branch was taken above: calls RtlWow64GetCpuAreaEnabledFeatures and stores the result in CpupCpuAreaEnabledFeatures — the same global RunSimulatedCode checks before deciding whether an XSTATE restore is required, and which gates all of BTCpuThreadInit's work.
confirms the publicly known description
Prior public discussion of WOW64CPU describes CpupSystemCallFast as being set when the process isn't under the dynamic-code-prohibition mitigation and a protection change on KiFastSystemCall succeeds. Direct tracing confirms this and adds the second half of the picture: the same function is also where the CPU-area feature mask that governs XSTATE handling throughout the rest of the module gets its one-time value.

wow64cpu!BTCpuResetToConsistentState

exportedrecovery / re-arm path

Unlike the Get/SetContext pair, this does not take a thread handle — its argument is a pointer to a structure holding a native AMD64 CONTEXT, used to rebuild a valid 32-bit guest context and re-arm the thread's CPU area so simulated execution can resume normally. The shape and placement strongly suggest this is the recovery path taken after something interrupts normal simulation — most plausibly an unhandled exception during 32-bit execution — rather than something exercised on every ordinary mode switch. 

// derived; structure of the rcx argument only partially known
NTSTATUS BTCpuResetToConsistentState(
    PVOID Unknown  // rcx — [rcx] is a destination struct ptr,
                    // [rcx+8] a pointer to a native AMD64 CONTEXT-shaped struct
);

behaviour

  1. Reads [rcx+8] — a native AMD64 _CONTEXT (see Structures) — and checks its SegCs field (offset +0x38, confirmed against the resolved structure layout) equals 0x23, the standard 64-bit code-segment selector. If it doesn't match, the function is a no-op and returns immediately — it only does real work when the current native context is genuinely running in 64-bit mode.
  2. Calls RtlWow64GetCpuAreaInfo for the current thread, fast-failing (int 29h) on failure — same pattern used throughout the module.
  3. Calls RtlpWow64CtxFromAmd64 to convert the native AMD64 context into the 32-bit guest context shape. The flags passed (0x1003F vs. 0x1007F) are chosen based on whether CpupCpuAreaEnabledFeatures is set, consistent with the extra bits requesting the XSTATE-extended portion of the conversion when extended features are enabled.
  4. Sets a flag bit on the converted context and clears another (likely marking it valid / clearing an in-progress indicator), then copies a field within the CPU area from offset +0xE8 to +0x98.
  5. Installs the address of CpupReturnFromSimulatedCode into the CPU area's return-address slot (offset +0xF8) — the same slot RunSimulatedCode reads on every mode switch. This explicitly re-points the next transition back at the normal simulated-code return path.
  6. Writes the 32-bit user-mode code selector (0x33) into the context, and finishes by writing the 32-bit data/stack selector (0x2B) and copied field values out to the destination structure at [rcx].
reading between the lines
Every individual piece here — the CS sanity check, the return-address re-arm, the selector hardcoding — points at the same purpose: forcibly restoring a thread's CPU area to a known-good state from which RunSimulatedCode can safely resume, after something (most plausibly exception handling) has left it in an inconsistent state. The name is not misleading.

wow64cpu!BTCpuThreadInit (undocumented export)

exported, not in the commonly-quoted listcalled once per thread

Not among the export names usually quoted for WOW64CPU.DLL, but present in this build and clearly load-bearing — it precomputes a pointer that RunSimulatedCode depends on. Called once per thread, presumably from the WOW64 thread-attach path mirroring BTCpuProcessInit's process-attach timing. 

NTSTATUS BTCpuThreadInit(VOID);  // no arguments consumed

behaviour

  1. If CpupCpuAreaEnabledFeatures (set once, process-wide, in BTCpuProcessInit) is zero, the function does nothing further and returns success immediately — everything below only runs when extended CPU-area features are actually enabled for this process.
  2. Otherwise, calls RtlWow64GetCurrentCpuArea for the current thread, fast-failing via int 29h on a negative status.
  3. Computes a pointer from the returned CPU area: a fixed offset (0xCC) plus a variable field read from that same area (offset 0x2DC), and stores the result into the TEB at offset 0x14D8.
why this matters for RunSimulatedCode
That same TEB slot — confirmed via dt ntdll!_TEB to be TlsSlots[1], not a dedicated named WOW64 field — relative offset 0x14D8, is exactly what RunSimulatedCode reads before deciding whether to call RtlXRestore on the way into 32-bit mode. BTCpuThreadInit's entire purpose is computing that pointer once, at thread creation, rather than re-deriving it on every mode switch.

wow64cpu!RunSimulatedCode (internal)

not exportedthe actual mode switch

Not part of the public contract — this is the function BTCpuSimulate loops on, and it is where the processor is actually switched between 32-bit compatibility mode and 64-bit long mode. Two paths through it were identified:

  1. Entry into 32-bit mode. Loads the thread's saved 32-bit register state from its CPU area, builds an IRET frame on the stack targeting the 32-bit code and stack selectors, and executes iretq to drop into 32-bit compatibility mode.
  2. Return from 32-bit mode, at the label CpupReturnFromSimulatedCode. Reached when the 32-bit code re-enters 64-bit mode — typically via the system call thunk. Swaps rsp/r14, saves the 32-bit register state back into the CPU area, and captures rflags.

Between those two paths sits a check of a bit in the CPU area (cleared via btr) that decides whether an FPU/SSE state restore (fxrstor) is needed before re-entering 32-bit mode — skipped on the fast repeated-syscall path where the state is already known current, performed on the slower path after other work may have touched it.

wow64cpu!TurboDispatchJumpAddressStart / …End (data)

data label, not a function32 × 8-byte entries

Despite appearing in the export table alongside the BTCpu* functions, these two symbols bound a 32-entry table of code addresses, not a callable routine — GetProcAddress resolves them to addresses, but calling either as a function is meaningless. TurboDispatchJumpAddressStart is in fact itself the dispatch stub: it takes the top bits of the system call number and jumps through the table indexed by that value. ...End marks the table's closing bound, most likely so external code — WOW64.DLL, when deciding whether a given return address falls inside the turbo-dispatch region — can range-check against it rather than because it is itself meant to be entered.

ntdll!RtlWow64GetCpuAreaInfo

ntdll.dll, not wow64cpu.dllshared across all binary translators

Not specific to WOW64CPU — this lives in NTDLL and is available to any binary translator DLL. Given a pointer to a CPU area, works out which architecture it belongs to and how large a context buffer is needed to describe it, accounting for both the fixed legacy register set and whatever extended (XSTATE) features are enabled on the machine. 

// derived; parameter roles inferred from usage, not from a header
NTSTATUS RtlWow64GetCpuAreaInfo(
    PVOID  CpuArea,        // rcx — pointer to the CPU area being queried
    USHORT MachineType,    // rdx — 0 defers to the area's own stored tag
    PVOID  AreaInfo        // r8  — output: sizes/offsets, caller-allocated
);

behaviour

  1. Reads a 16-bit machine-type tag from the CPU area (offset +2), unless the caller supplied one directly in rdx.
  2. Switches on that tag against four recognised values, each corresponding to a supported guest architecture. An unrecognised tag returns STATUS_INVALID_PARAMETER.
  3. For the matched architecture, calls RtlpGetLegacyContextLength to get the fixed legacy-context size.
  4. Calls RtlGetExtendedContextLength2 to compute the additional XSTATE-extended size, gated by a feature mask read from a KUSER_SHARED_DATA field.
  5. Combines both sizes with alignment rounding and writes total size, extended-region offset, and machine-type back into the caller's output structure.
why BTCpuGetContext/SetContext need this
Before copying a context in or out of a CPU area, the module needs to know exactly how large that context is for the current architecture and feature set — this function (or its ...CurrentCpuArea sibling) is what answers that question.

ntdll!RtlWow64GetCurrentCpuArea

ntdll.dll, not wow64cpu.dllsibling of RtlWow64GetCpuAreaInfo

Functionally identical to RtlWow64GetCpuAreaInfo, but operates on the calling thread's own CPU area rather than one supplied by the caller — fetched directly from the TEB's TlsSlots[1] (offset +0x1488; confirmed via dt ntdll!_TEB to be an ordinary TLS slot, not a dedicated named WOW64 field) at the start of the function. 

NTSTATUS RtlWow64GetCurrentCpuArea(
    PUSHORT  MachineType,     // rcx — optional, null-checked before write
    PVOID    SizeInfo,        // rdx — optional, null-checked before write
    PVOID   *CpuAreaPointer   // r8  — optional, null-checked before write
);

behaviour

Same architecture-tag switch, same calls into RtlpGetLegacyContextLength and RtlGetExtendedContextLength2, same size/offset computation as RtlWow64GetCpuAreaInfo. The three output parameters are each individually optional — the function checks each pointer for null before writing through it, so a caller can request just the machine type, just the size info, just the CPU area pointer, or any combination.

this is the one BTCpuGetContext/SetContext actually call
Both BTCpuGetContext and BTCpuSetContext call this current-thread variant, not the general ...CpuAreaInfo form — makes sense, since both are always operating relative to the calling thread's own cached state on the fast path.

ntdll!RtlGetExtendedContextLength2 (partially verified)

ntdll.dllshared XSTATE sizing helper

The function both RtlWow64GetCpuAreaInfo and RtlWow64GetCurrentCpuArea call to size the XSTATE/extended-state portion of a context. This is the most complex function traced for this page, and the branch-level detail below should be read as a structural description, not a guarantee of bit-exact correctness in every path. 

// derived; least confident signature on this page
NTSTATUS RtlGetExtendedContextLength2(
    ULONG    ContextFlags,   // ecx
    PULONG   Length,         // rdx — out
    PULONG64 FeatureMask     // r8  — hypothesized role
);

behaviour (structural)

  1. Validates the requested ContextFlags against several bitmask patterns; combinations that don't match any recognised pattern return STATUS_INVALID_PARAMETER or STATUS_NOT_SUPPORTED depending on which check fails.
  2. Derives a base size from a small set of fixed constants selected by which flag bits are set.
  3. Walks a 64-bit XSTATE feature mask bit by bit (up to 64 iterations), accumulating size and alignment for each enabled feature by indexing into per-feature tables published in SharedUserData (offsets +0x5F8 and +0x604 observed) — the standard mechanism Windows uses to publish XSTATE feature geometry to user mode without a system call.
  4. Writes the accumulated total back through Length.
explicitly flagged as incomplete
The overall shape — flag validation, then a per-feature accumulation loop driven by SharedUserData tables — is solid. The exact meaning of every individual bitmask constant compared against ContextFlags is not. Do not treat the constants in this section as verified; confirm against live Windows behaviour (varying flag combinations and comparing returned lengths) before relying on them for an implementation.

ntdll!RtlpGetLegacyContextLength

ntdll.dll, private (note the p)4 instructions of real logic

The smallest of the RTL support functions. A straight bit-test switch returning a fixed size constant for the non-extended, legacy portion of a context, per architecture. 

VOID RtlpGetLegacyContextLength(
    ULONG  ArchitectureFlags,  // ecx
    PULONG Length              // r8 — optional, null-checked
);

behaviour

Tests bits 0x10, 0x14, 0x15, and 0x16 of the input flags in sequence, returning 4, 0x10, or 8 bytes depending on which bit is set — the size of the base (non-XSTATE) register block for that architecture family. If Length is non-null, the result is additionally written through it; the value is always also returned directly in eax.

ntdll!RtlpWow64CtxFromAmd64

ntdll.dll, private (note the p)traced to completion

Converts a native AMD64 CONTEXT into a 32-bit guest WOW64_CONTEXT, group by group. Called from BTCpuResetToConsistentState whenever a native context needs to be reflected back into guest form. The trace now reaches the function's actual ret, so the group-by-group structure below is complete, though a couple of individual field identities within each group are inferred from offset patterns rather than confirmed against a named structure. 

// derived; field-level identity of some offsets inferred, not confirmed
VOID RtlpWow64CtxFromAmd64(
    ULONG  ContextFlags,        // ecx
    PCONTEXT NativeContext,     // rdx — source, native AMD64 context
    PWOW64_CONTEXT GuestContext  // r8  — destination, 32-bit guest context
);

behaviour

The function works through the requested ContextFlags one group at a time. Every group follows the same shape: test whether the group's bit is set in both a caller-independent mask and the flags already present in the destination buffer, and only then copy that group's fields and OR the group's bit into an output flags accumulator kept in edi. Field names below are resolved against the public _CONTEXT layout (source) and the standard x86 CONTEXT layout (destination) — see Structures → _CONTEXT.

the destination side (WOW64_CONTEXT / x86 CONTEXT)
ntdll!_WOW64_CONTEXT doesn't resolve by name in this build's public symbols, but the destination offsets used throughout this page (+0x9C Edi, +0xA0 Esi, +0xA4 Ebx, +0xA8 Edx, +0xAC Ecx, +0xB0 Eax, +0xB4 Ebp, +0xB8 Eip, +0xBC SegCs, +0xC0 EFlags, +0xC4 Esp, +0xC8 SegSs, +0x8C–+0x98 the remaining segment registers, +0xCC the 512-byte ExtendedRegisters array) match the long-published, standard x86 CONTEXT layout exactly, so they're used by name throughout the rest of this page even though the type itself couldn't be resolved directly from this build's symbols.

the per-thread CPU area (no Microsoft name found)

no public typeTEB->TlsSlots[1]offset table only

Every BTCpu* function on this page reads or writes this structure, and it is reached from an ordinary TLS slot (TEB->TlsSlots[1], confirmed via dt ntdll!_TEB) rather than a dedicated named field. No type name for it was found anywhere in this build's public symbols — dt against every plausible name (_WOW64_CPURESERVED, _WOW64_CPU_RESERVED, _CPU_AREA_INFO) failed, wildcard symbol search (x ntdll!*CPURESERVED*, x ntdll!*Wow64Reserved*) turned up nothing, and the architecturally-adjacent _CHPEV2_CPUAREA_INFO (the ARM64/CHPE equivalent, which is named) doesn't resolve either. This appears to be genuinely nameless in any available symbol source, not merely unresolved by a wrong guess.

methodology

Everything on this page was derived from live behaviour: register state, stack contents, and call stacks captured with WinDbg attached to an ordinary 32-bit process (Notepad, running under SysWOW64) on a 64-bit Windows installation, cross referenced against the disassembly of the functions actually reached during those traces. WOW64CPU.DLL cannot be loaded directly by user code for inspection — it is mapped into a process by NTDLL's own WOW64 initialisation before any of the process's own code runs — so it can only be examined this way, by attaching to a process that already has it resident and switching the debugger's effective machine to amd64 to see the 64-bit side of the address space.

No Microsoft source code, private symbol server content beyond ordinary public symbols, or disassembler/decompiler output has been reproduced verbatim anywhere on this page — every description here is a restatement, in the author's own words, of what was observed to happen, in the same spirit as (though with nothing like the thoroughness of) the reverse-engineering notes published for years at geoffchappell.com.
